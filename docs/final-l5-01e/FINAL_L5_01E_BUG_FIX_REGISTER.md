# FINAL-L5-01E — Bug Fix Register

## L5-01E-001: Duplicate `useStaffContext()` instances on `/staff/dashboard`
- **Evidence**: `grep -rn "useStaffContext"` showed two independent call sites — `components/layout/StaffLayout.tsx:27` and `app/staff/dashboard/page.tsx:11` (pre-fix) — each mounting its own `useEffect`/`useState` cycle and firing its own `/v1/auth/me` request.
- **Severity**: Medium (correctness/waste, explicit rule 8 violation; not itself the dominant cause of the observed redirect flakiness once isolated — see Root Cause Report).
- **Root cause**: `StaffLayout` was written as a reusable wrapper component (not a Next.js route `layout.tsx`), so each page manually renders `<StaffLayout>{content}</StaffLayout>` around its own JSX. The dashboard page additionally called the auth hook itself, duplicating work `StaffLayout` already does.
- **Fix**: Added `StaffContextProvider`/`useStaffContextValue()` to `hooks/useStaffContext.ts`. `StaffLayout` is now the sole caller of `useStaffContext()` and shares its resolved value via React Context. `StaffDashboardPage` now renders `<StaffLayout><StaffDashboardContent/></StaffLayout>`, and `StaffDashboardContent` consumes `useStaffContextValue()` instead of re-fetching. This also means the dashboard's 5 `useApi()` data fetches (skills/jobs/notifications/service-areas/status) no longer fire before auth is confirmed — they only mount once `StaffLayout` has already resolved the technician as authenticated.
- **Regression test**: `e2e/tenant-portal/final-l5-01e-technician-auth-regression.spec.ts` — asserts `/v1/auth/me` is called at most twice per cold login (2 = React Strict Mode's dev-only double-invoke of a single hook instance; a real second call site would push this to 4). `npx tsc --noEmit`: 0 errors.
- **Final status**: **FIXED, verified via TypeScript, source-level re-grep (single call site confirmed), and live browser regression test.**

## L5-01E-002 (found, not fixed — pre-existing, out of scope): `clearSession()` redirects to `/login`, not `/staff/login`
- **Evidence**: `frontend/tenant-portal/lib/api.ts:54` — `clearSession()` (invoked on an unrecoverable 401 from any authenticated call) hard-navigates to `/login` (the tenant-owner login page) unconditionally, regardless of which app the session belonged to.
- **Severity**: Low for the technician flow specifically — no 401 was observed against a freshly issued token in any of this sprint's 65 real-browser runs (see Root Cause Report: access tokens have an 8-hour expiry, ruling out near-login expiry as a trigger). This is a real latent bug for a technician whose session genuinely expires *during* a long session (e.g. an 8+ hour shift) — they would be misrouted to the owner login page instead of `/staff/login`.
- **Root cause**: `clearSession()` is shared, app-wide code with a single hardcoded redirect target that predates the staff app.
- **Fix**: Not applied — this is a pre-existing, general-purpose function used across the whole tenant-portal (owner pages too, where `/login` is correct); making it staff-aware (e.g. checking the current path) is a real but separate fix outside this mission's explicit scope (technician redirect *after login*, not session-expiry routing during a session). Documented here rather than silently left out.
- **Final status**: **DOCUMENTED, not fixed** — carried to Remaining Blockers as a low-severity, non-blocking item.
