# MODULE-L5-00 — Module Registry (narrative)

Full machine-readable detail: `docs/module-l5/03-module-registry.json`, generated by `e2e/module_inventory_scan.py` (source-derived — not a hand-typed duplicate of `app/engines/*`). This is a **first-pass, directory-level inventory classification**, appropriate for an L00 gate. It is explicitly not a deep per-module layer-matrix certification (Part 6) — that level of depth is out of bounded scope here and belongs in each module's future `MODULE-[ID]-L1` sprint.

## Method and honest limitations

For each of the 68 real `app/engines/*` module directories, the scanner records: whether it declares an `APIRouter(...)`, how many `@<var>.{get,post,put,patch,delete}(` endpoints exist across its files (any router variable name, not just literally `router`), whether any model file defines `__tablename__`, whether a name-matching test file exists in `tests/`, and whether a name-matching route directory exists under `frontend/super-admin/app` or `frontend/tenant-portal/app`.

**The frontend-route and test-file matches are name-substring heuristics, not semantic verification** — a match means "a plausibly-related file exists," not "this module's UI/tests were confirmed to actually call the right endpoints." This limitation is deliberate and stated per Non-Negotiable Rules 8-9 ("do not assume every endpoint has a usable UI" from a naive check) — false positives and false negatives are both possible and are exactly why `COMPLETE_PROVISIONAL` (not `COMPLETE`) is the ceiling classification this sprint can honestly award.

## Real finding: `vertical_billing` is an orphaned duplicate scaffold, not an active module

`app/engines/vertical_billing/` contains only `constants.py` (64 lines) and `__init__.py` — its own docstring claims **"Proven Level 5"** and describes a `VerticalBillingConfig`-driven architecture. Direct search confirms `VerticalBillingConfig` is real and implemented — but entirely inside **`app/engines/platform_commerce/`** (`billing_constants.py`, `billing_models.py`, `billing_router.py`), not in `vertical_billing`. This is a genuine `DUPLICATE_ENGINE` / `PLACEHOLDER` finding (Parts 14 and 18): a module directory whose own documentation falsely implies completion, when the real, working implementation lives elsewhere under a different name. **Classification: `PLACEHOLDER` / `DEAD_SCAFFOLD`, not an active module** — correctly excluded from "active module" counts for the zero-unknown guard (see `35-guard-results.md`).

## `BACKEND_ONLY_CANDIDATE` modules (17) — real candidates for Part 16 investigation

`ai_conversation` (16 endpoints), `auth` (96 — expected, mostly internal/shared-infra), `coaching_appointment` (15), `dashboard_command_center` (20), `entitlement` (11), `final_records` (31), `home_service_booking` (16), `public_registration` (6), `real_estate_lead` (20), `serviceability` (29), `trust_quality` (24), `vertical_catalog` (9), plus 5 more found after the regex fix.

Several of these are legitimately `BACKEND_ONLY_ACCEPTABLE` on inspection, not blockers:
- `auth` — shared infrastructure consumed by every frontend, correctly has no dedicated "auth module" page.
- `public_registration` — consumed by a registration flow that lives under a different frontend route name (`onboarding`, not `public_registration` — a heuristic false positive, not a real gap).
- `real_estate_lead`, `coaching_appointment` — these back the AI-chatbot-driven vertical flows (Sprint 17/18 in this repo's history) whose UI lives in the chat/conversation surface, not a dedicated named page — same heuristic false-positive pattern.

Genuinely worth a real Part-16 investigation in a future sprint (endpoints exist, no obvious alternate UI found on inspection): `entitlement`, `trust_quality`, `dashboard_command_center`, `vertical_catalog`, `final_records`.

## `PARTIAL_UNTESTED` modules (6) — real candidates for Part 19 investigation

Have a frontend route match but no matching test file — worth checking whether they're covered under a differently-named test file (as `finance_hub` is) or are genuinely undertested. Full list in the JSON registry (`status_firstpass == "PARTIAL_UNTESTED"`).

## What this sprint does not claim

This registry does **not** certify any module as functionally complete. `COMPLETE_PROVISIONAL` is explicitly a directory-level signal, not a runtime-verified one — per this program's own Mandatory Clause, "a module is complete only when every required layer and workflow is implemented, integrated, persisted, permission-controlled, tenant-safe, audited, notified, automated where required and runtime-tested," none of which this first-pass scan verifies. Deep layer-matrix work (Part 6) is deferred to each module's future `MODULE-[ID]-L1..L5` sprint sequence (see `33-implementation-roadmap.md`).
