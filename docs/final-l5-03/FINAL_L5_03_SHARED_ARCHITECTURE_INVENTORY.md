# FINAL-L5-03 — Shared Architecture Inventory

Scope: `frontend/super-admin`, `frontend/tenant-portal` (includes `/staff/*` — there is **no separate Staff/Technician frontend app**; it is a route family within tenant-portal, confirmed via `ls frontend/` and prior sprints' work on `/staff/*`), `frontend/customer-app`, `app/` (backend). All findings below are from direct grep/read this sprint, not carried assumptions.

| # | Item | Finding |
|---|---|---|
| 1 | API client implementations | **3 independent clients**, one per app: `frontend/super-admin/lib/api.ts`, `frontend/tenant-portal/lib/api.ts` (both a private `apiFetch<T>()` + typed domain exports, near-identical shape), `frontend/customer-app/lib/api/client.ts` (+ `auth.ts`, `customer-home-services.ts`). No shared npm package — each app owns its client. Duplicate-equivalent: yes, structurally (same `ApiResponse`/`ServiceOSError`/401-refresh shape), but each app has a different token key, different tenant-context need, and different domain surface — **duplication is justified per rule 5** (not "without reason"), not a candidate for forced merging into one shared package this sprint (would be a cross-app build-tooling change, high blast radius, no current test harness for a shared package). |
| 2 | Auth/session implementations | Each app: login page → `authApi.login()` → localStorage token write → redirect. **Found and removed this sprint**: both super-admin and tenant-portal login pages had a `MOCK_MODE` (`NEXT_PUBLIC_USE_MOCK` env-gated) bypass that stored a fake token and skipped real auth entirely — disabled in `.env.local` but a live, reachable code path in the shipped bundle. Removed (see Auth Session Regression Report). |
| 3 | Token storage/refresh | `localStorage` keys differ per app by design (`serviceos_admin_token`, `serviceos_tenant_token`, customer-app's own key) — tenant/admin/customer are different security principals, so distinct keys are correct, not accidental duplication. Refresh logic (401 → `/v1/auth/token/refresh` → retry once → `clearSession()`) is duplicated near-identically across the 3 `apiFetch` implementations — same justification as #1. |
| 4 | Permission/role helpers | `isTenantReadOnly()` (JWT `access_scope`-based) exists centrally in tenant-portal's `lib/api.ts` (from FINAL-L5-01D). **Found**: `provider/status/page.tsx` and `provider/offerings/page.tsx` each duplicated an identical inline `role === "tenant_owner" \|\| role === undefined` check instead of using a shared helper. **Fixed this sprint** — extracted to `isTenantOwnerRole()`. No formal `can()`/`canAny()`/`PermissionContext` registry exists (see Permission Architecture Report for why a full registry build-out is not attempted this sprint). |
| 5 | Tenant-context helpers | `getTenantId()`/`getUserRole()`/`getUserId()` centrally in tenant-portal's `lib/api.ts`. **Found**: `admin/finance/usage-credits/page.tsx` has a hardcoded `DEMO_TENANT_ID` fallback constant — flagged in Tenant Context Report, not changed (admin cross-tenant tooling legitimately needs a tenant-id input field; the hardcoded default is a dev convenience, not a security bypass, since the real value always comes from the input field / URL param when present). |
| 6 | Query/cache libraries | **None** — confirmed in FINAL-L5-01E's investigation and re-confirmed this sprint: `useApi`/`useAction` (hand-rolled local-state hooks, one instance per call site, `useRef` guard against stale responses within one instance) is the sole pattern across all 3 apps. No React Query/SWR. This is an established, working pattern — not something this sprint replaces (would be a genuine rewrite, forbidden by rule 1 without stronger evidence of need). |
| 7 | Route configuration | `lib/page-registry.ts` + `lib/nav-config.ts` exist in both super-admin and tenant-portal (customer-app has no equivalent — small, fixed route set, no dynamic nav needed). Not a shared package; per-app. Audited, not restructured this sprint (Part 16 explicitly defers menu redesign to L5-04/05). |
| 8 | Navigation configuration | Same files as #7. |
| 9 | Status maps | `lib/status-labels.ts` + `lib/status-format.ts` (tenant-portal only) exist per app. |
| 10 | Form components | Plain controlled `<input>`/`<Input>` shared component per app's `components/shared/ui.tsx`; no schema-validation library (e.g. no react-hook-form/zod) in any of the 3 apps — validation is inline, backend-authoritative (matches rule 8). |
| 11 | Table/grid components | `EnterpriseDataGrid` (super-admin AND tenant-portal both have a copy) is the canonical data-grid; a separate, unused `DataTable` exists in each app's `ui.tsx` (0 consumers in tenant-portal, 31 consumers in super-admin — per FINAL-L5-00's dead-code report, re-confirmed relevant). |
| 12 | Loading states | `Skeleton` component per app's `ui.tsx`. **Found and fixed this sprint**: 3 instances of `<Skeleton/>` (renders a `<div>`) nested directly inside a `<p>` tag on the Tenant Dashboard — invalid HTML, caused a real SSR/client hydration mismatch on every dashboard load (browser-verified, now fixed). |
| 13 | Empty states | `EmptyState` component per app's `ui.tsx`, widely used (17-18 consumers per app per FINAL-L5-00). |
| 14 | Error states | `ApiErrorAlert`/`ApiErrorState`-equivalent patterns exist inline per page (no single shared component across all error types the mission recommends — see Error Handling Standard). |
| 15 | Toast/notification components | `Toaster`/`ToastItem` in tenant-portal's `TenantLayout.tsx`; similar per-app patterns. |
| 16 | Modal/drawer components | `Modal` in each app's `ui.tsx`; `SetupWizardDrawer` (tenant-portal, `TenantLayout.tsx`) — **this is where the dormant-wallet 500/CORS bug was found and fixed this sprint** (see Business Rule/Performance reports). |
| 17 | File-upload components | `mediaApi.initiateUpload()` + direct `PUT` to a pre-signed `upload_url` (tenant-portal `media/page.tsx`) — correctly bypasses the shared client for the storage PUT itself (valid special case, documented in Direct Fetch report). |
| 18 | Theme/design-token systems | `lib/design-tokens.ts` per app (super-admin, tenant-portal); dark/light mode via `useTheme()` hook. Not consolidated into a shared package this sprint (audit-only, see Design Token Report). |
| 19 | Logging utilities | Backend: `structlog`, used in 267 files (per FINAL-L5-00). Frontend: `lib/authTimeline.ts` (tenant-portal, FINAL-L5-01E) is the only dedicated frontend logging utility, explicitly no-secrets by design. |
| 20 | Request ID handling | Backend: `RequestIDMiddleware` + `request_id` in every `ApiResponse`. Frontend: `ServiceOSError.requestId` preserved through `apiFetch`'s error path in all 3 apps — **except** the 5 super-admin pages found this sprint, which discarded `request_id` entirely (`throw new Error(json?.error?.message)`) — fixed by routing through the shared client. |
| 21 | Browser E2E helpers | No shared login-helper module — every FINAL-L5-* sprint's Playwright specs re-implement `waitHydrated()`/`login()` inline per spec file (a real, acknowledged duplication — see Test Infrastructure Report for why a shared helper is recommended but not extracted this sprint, given the specs are ad-hoc evidence scripts, not a permanent CI suite). |
| 22 | Shared backend dependencies/helpers | `get_current_user`, tenant-scope dependencies, `ok()`/error envelope helpers audited in Backend Shared Helper Report — found a real issue: **500 error responses are missing CORS headers** (browser reports "CORS blocked" instead of the real 500, masking failures) — documented as a real, non-trivial middleware-ordering risk, not blind-fixed this sprint given its security-sensitive nature (see that report for the specific reasoning). |
