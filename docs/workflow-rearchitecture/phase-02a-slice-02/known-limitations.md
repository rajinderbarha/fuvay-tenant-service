# Known Limitations

1. **5 files still contain placeholder-role-shaped arrays**, unfixed this slice: `notifications/templates/page.tsx` (`AUDIENCES`), `checklists/page.tsx` (`OWNER_ROLES`), `compliance/page.tsx`, `intelligence/page.tsx` (`ALL_ROLES`), `workflow-templates/page.tsx`. These appear to be audience/ownership *tags* for templates/checklists/workflows rather than live `User.role`-writing selectors, but that was not confirmed for each one individually — fixing them without confirming whether each tag has a real downstream authorization consequence risks an incorrect semantic mapping (e.g., guessing that a "compliance_officer" tag should become "admin_security" when the actual intended audience might be different).
2. **Backend `require_super_admin` gating gap unchanged.** Nav items now correctly show/hide for admin_operations/finance/security/readonly based on real permissions, but many backend routes those roles could now see in nav are still hard-gated to `role == "super_admin"` only (Phase 1A `backend-blockers.md` #7). This is a large (~29-file) backend authorization architecture change, out of scope for a navigation slice.
3. **My Work badge causes a duplicate network call** when the `/staff/my-work` page itself is open (layout-level badge fetch + page-level content fetch, not deduplicated/cached).
4. **Staff (office manager) shell remains merged with technician's**, not built as its own distinct 7-item grouping — doing so would require new Team/Customers/Business pages that don't exist in this shell yet.
5. **Tenant-owner shell not remapped** to the approved 9-item grouping — still uses its pre-existing 8-group structure (Overview/Setup/Team/Operations/Finance/Engagement/Insights/More).
6. **Breadcrumb reconciliation not done** — existing `Breadcrumbs` component untouched; not confirmed whether it produces good labels for the 6 newly-nav-added pages.
7. **No shared "route access state" component built** — existing per-surface handling (StaffLayout's access-denied message, My Work's partial-data banner, the new 410 response) is consistent in spirit but not unified into one reusable pattern.
8. **admin_readonly mutation-exclusion not exhaustively re-audited** — spot-checked 2 pages (`commission-records`, `payments`) which correctly gate their export action behind `perm.has(...)`; the other ~50+ admin pages' mutation buttons were not individually re-checked this slice.
9. **Pre-existing duplicate-operation-ID warnings** in `service_setup/templates_router.py` remain (unrelated, documented not fixed, same as Slice 1).
