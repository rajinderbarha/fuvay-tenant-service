# Duplicate / Concurrency Review

| Scenario | Classification | Rationale |
|---|---|---|
| Concurrent quote updates (two staff editing items simultaneously) | CONCURRENCY_RISK_DOCUMENTED | No optimistic-version field (`version`/`updated_at`-compare) on `ServiceJobQuote`; last-write-wins on the recalculated totals. Not fixed this slice (would require adding a version column — schema change, judged out of proportion; documented, not a security defect since both writers are already authorized). |
| Concurrent send actions | CONCURRENCY_SAFE (practically) | `_assert_transition` re-reads `q.status` at call time; a second concurrent `send_to_customer` call on an already-sent quote would fail `_assert_transition` (its in-memory `q` object may be stale, but the `UPDATE ... WHERE id = q.id` with a subsequent read would not silently double-apply — no duplicate `QEV_SENT_TO_CUSTOMER` event within a single request). True row-level race (two requests both passing `_assert_transition` before either commits) is a TOCTOU risk shared with the rest of this codebase's read-then-write pattern; not specific to this module. |
| Concurrent approve/reject | IDEMPOTENT (approve) / DUPLICATE_REJECTED (reject) | `customer_approve`'s idempotency-key mechanism makes repeated approval with the SAME key a no-op return; a DIFFERENT key on an already-approved quote raises `QUOTE_IDEMPOTENCY_CONFLICT`. `customer_reject` has no idempotency key, but `_assert_transition` rejects a second rejection attempt on an already-`customer_rejected` quote (terminal status, `QUOTE_TRANSITIONS[QS_CUSTOMER_REJECTED] == set()`). |
| Duplicate line items | DUPLICATE_REJECTED at the application level only | No unique constraint prevents two identical `(quote_id, item_name, item_type)` rows — a staff member could add the same line item twice via two separate `add_item` calls; this is not prevented, but also not the amount-integrity risk the mission is concerned with (each such call still validates/recalculates correctly, just may reflect intentional duplicate charges, e.g. two identical parts). Not fixed (no evidence this is unintended; a legitimate use case — ordering 2 identical parts — looks identical to an accidental duplicate at the data level). |
| Duplicate approval history | DUPLICATE_REJECTED | Covered by the idempotency-key + `_assert_transition` mechanisms above — no second `QEV_CUSTOMER_APPROVED`/`QEV_CUSTOMER_REJECTED` event can be written for the same quote. |
| Duplicate invoice creation from quote | DUPLICATE_REJECTED | `create_invoice`'s pre-existing "prevent duplicate active invoice per job" check (`ServiceInvoice.job_id == job.id, status.not_in([INV_CANCELLED])`) blocks a second invoice for the same job regardless of source — unaffected by this slice's fix, re-verified via full regression. |
| Optimistic version fields | Not present on any quote_checklist table | `ServiceOSBase` provides `created_at`/`updated_at` only, no `version` column. Consistent with the rest of this codebase's general pattern (documented as a cross-cutting characteristic, not unique to this module). |
| Row locks | Not used | No `SELECT ... FOR UPDATE` anywhere in this module — consistent with the codebase-wide pattern of relying on the database's default transaction isolation plus application-level idempotency/state checks rather than explicit locking. |
| Unique constraints | `quote_number` only (`uq_sjq_quote_number`) | Server-generated (`_quote_number()`, UUID-derived), collision probability negligible; no functional uniqueness gap. |
| Commit ordering | Validated-then-mutate-then-commit throughout | Every mutation method performs all validation (ownership, state, amount) before any `db.add`/`db.execute(update(...))`, and `db.commit()` is always the LAST statement — confirmed by source-position review of every method in `quote_service.py`/`checklist_service.py`, and by this slice's own fix to `invoice_service.create_invoice` (moved validation before `db.add`). |

## Summary
No integrity defect confirmed. One genuine concurrency risk (no optimistic versioning on quote totals) is documented, not fixed — it does not allow an unauthorized actor to do anything; it only affects which of two AUTHORIZED concurrent edits "wins," a product/UX question, not a security gap. Transaction infrastructure was not redesigned, per this slice's explicit scope limit.
