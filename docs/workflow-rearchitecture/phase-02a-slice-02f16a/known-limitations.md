# Known Limitations

- No live database/server verification was performed (unit tests + static/executed route introspection only), consistent with every prior slice.
- **Idempotent-repeat-approval short-circuit does not re-run total reconciliation.** `customer_approve`'s early-return path for a repeat call with the SAME idempotency key on an already-approved quote returns the stored `q.to_dict()` (with `provider_internal_notes` stripped) WITHOUT re-querying items to recompute a customer-visible-only total — unlike the full `_customer_dict` path used by the non-idempotent approve/reject/request-revision returns. This is a deliberate, narrow trade-off to preserve an existing test's `db.execute.assert_not_called()` contract for the idempotent path (a performance/simplicity choice from the original 2F-16-era design, not something this slice was asked to change). In practice this is low-risk: item mutation is already locked once a quote reaches `sent_to_customer` (2F-16's `ITEM_EDITABLE_QUOTE_STATUSES`), so the stored total at the moment of the ORIGINAL approval (which DID go through the full reconciling path) cannot have drifted by the time of a repeat call.
- `_recalculate`'s bucket coverage gap (`visit_charge`/`other` item types contribute nothing to the total) is a pre-existing characteristic, not introduced or worsened this slice — documented in `customer-visible-monetary-contract.md`, not fixed (would require new pricing policy, out of scope).
- `is_customer_visible` remains a single boolean with no sub-classification of WHY an item is hidden (cost vs. margin vs. bookkeeping) — documented, not fixed (schema change, out of scope).
- The `QUOTE_ACCESS_DENIED` error code still exists for tenant-scoped MUTATION paths (`_assert_tenant`, used by `add_item`/`update_item`/`cancel_quote`/etc.) — only the READ paths (`get_quote`/`get_checklist`/`list_quote_events`) were unified to the privacy-safe `*_NOT_FOUND` pattern this slice, per the mission's specific Workstream 9 scope (customer/foreign-tenant reads). A tenant/staff caller attempting a cross-tenant MUTATION still receives a distinguishable `ACCESS_DENIED` — judged acceptable since tenant/staff callers are not the "external" privacy-sensitive audience the mission's closure requirement targets (customers/foreign records), and unifying mutation-path errors was not requested.
- Coverage denominator (227) reflects only routes accumulated across this initiative's own slice history, not a full-codebase audit.
