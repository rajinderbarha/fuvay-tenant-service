# Known Limitations

- No live database/server verification was performed (unit tests + static/executed route introspection only), consistent with every prior slice.
- The account-validity component of the trusted-creation predicate (`changed_by_user_id references a real, active, non-deleted canonical customer account`) is satisfied TRANSITIVELY at write time (via `get_current_user`'s authentication requirement), not re-verified retroactively against the account's CURRENT state every time the historical creation event is read. If a customer account is deactivated/deleted after having legitimately created a Booking, that Booking's creation-history row still satisfies the actor-binding predicate (correctly — the creation event genuinely happened as recorded); whether such Bookings should lose relationship-evidence trust upon the creator's later deactivation is a product question (see `product-decisions-required.md`), not a security gap in the code as it exists.
- Duplicate/conflicting `from_status IS NULL` rows for one Booking remain a THEORETICAL, not database-enforced, impossibility — guaranteed only by the fact that exactly one writer (`create_booking`) ever produces such a row, called at most once per Booking in the current codebase. No unique constraint exists at the schema level. Documented, not fixed (would require a migration, out of scope).
- The two canonical CSVs (`tenant-mutation-endpoint-inventory.csv` and `mutation-enforcement-matrix.csv`) intentionally use different denominator conventions (tenant-only rows vs. total-mounted-routes-per-module) — see `canonical-csv-structure.md`. This is a pre-existing, unchanged-by-this-slice characteristic of the initiative's documentation structure, not a new inconsistency.
- Coverage denominator (216) reflects only routes accumulated across this initiative's own slice history, not a full-codebase audit.
