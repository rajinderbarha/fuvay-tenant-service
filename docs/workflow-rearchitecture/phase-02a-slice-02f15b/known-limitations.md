# Known Limitations

- No live database/server verification was performed (unit tests + static/executed route introspection only), consistent with every prior slice.
- The "no conflicting creation-history rows" guarantee is a code-path argument (only one call site in the entire codebase ever writes `from_s=None`, and only once per Booking via the normal `create_booking` flow), not a database-level uniqueness constraint. A direct-DB-insert bypass of the service layer could theoretically create a second `from_status IS NULL` row for one Booking; this is documented as a theoretical risk in `missing-history-legacy-behavior.md`, not fixed (would require either a migration-level constraint or an application-level uniqueness check, both judged out of proportion to a risk with no known trigger path in this codebase).
- The provider-assisted provenance mechanism rechecks independent evidence at each authority-dependent action rather than persisting a one-time trust decision — this trades a small amount of per-action query cost for avoiding a new schema column/migration and a stale-trust-flag risk; see `provider-assisted-provenance.md` for the full rationale.
- `access_scope`'s absence for customer accounts is relied upon as the mechanism that keeps `require_tenant_mutation_permission` independent of tenant mutation scope for customers — this is correct in the current token-issuance code, but is an implicit property (no code explicitly asserts "customers never have access_scope"), not a structurally enforced invariant. A future change to customer token issuance that accidentally sets `access_scope` could regress this; the defensive test (`test_customer_user_with_forged_readonly_scope_is_denied`) proves the dependency still fails safely (denies) in that scenario, so the risk is fail-closed, not fail-open, even if it occurred.
- Coverage denominator (220) reflects only routes accumulated across this initiative's own slice history, not a full-codebase audit.
