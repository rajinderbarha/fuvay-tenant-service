This investigation went deeper than the original file-level grep and found that the true
consumer graph is **larger than the 12-file inventory FINAL-L5-05G produced** — FINAL-L5-05G's
grep matched only direct callers of `ledger.py`'s named functions
(`credit_wallet`/`debit_wallet`/etc). It did not catch router/service files that mutate
`TenantWallet`/`WalletTransaction` **directly on the model** (bypassing `ledger.py` entirely) or
files that call a *different* commission/wallet ledger built on separate tables. Both are real
and are documented below as new findings, not folded silently into the original 11.

**Result: 0 of the 11 remaining consumers are classified UNKNOWN.** Every one has a named, evidenced financial domain and disposition. However, the investigation surfaced that the *true* number of independent, un-reconciled financial-mutation code paths touching `TenantWallet`/`tenant_billing` is **at least 5 separate "admin adjusts a tenant's credit balance" implementations** (platform_commerce `admin_credit_wallet`, field_ops `admin_wallet_topup`/`admin_wallet_adjust`, tenant_engine `credit_topup`/`credit_adjust`, package_commerce `admin_topup_wallet`/`admin_adjust_wallet`, invoice_payment `ProviderCreditWalletService.admin_credit`) and **4 separate commission-deduction implementations** (platform_commerce `CommerceService.deduct_commission` via field_ops, invoice_payment `ServiceCommissionService`, plus the already-blocked `engine_deduct_wallet`, plus the customer_credits dispute-settlement wallet-recovery leg which is deduction-shaped but not labeled "commission"). This is real evidence of an architecture that grew multiple parallel implementations for the same conceptual operation across different sprints, not a single shared domain with multiple call sites.
