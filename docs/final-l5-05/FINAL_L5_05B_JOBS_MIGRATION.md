## Decision (Part 2 required outcome)
1. **Canonical Jobs list route**: `/admin/home-services/service-jobs` (once parity is closed).
2. **Canonical Jobs detail route**: `/admin/home-services/service-jobs/[jobId]` (once parity is closed).
3. **Create/action ownership**: mutation actions (reassign, status override, force-close, void) do not yet exist against `service_jobs` at all — they must be built (new backend endpoints + new UI), not simply "pointed" at from the canonical page, before the canonical page can safely become primary.
4. **Legacy redirect behavior**: `/admin/operations` keeps its existing real "legacy Field Ops" self-disclosure banner and its link to the canonical page (already present — verified via a new regression test) until migration is complete; it is NOT redirected away yet, because doing so today would silently remove reassign/override/force-close/SLA-tracking/summary-stats from admin users with no replacement.
5. **Removal/deprecation**: not scheduled this sprint — real replacement functionality must exist first (rule 5: "do not remove working job actions").

## What was fixed this sprint (real, live-verified)
Two backend endpoints (`assignment-timeline`, `execution-timeline`) and one endpoint (`notes`) already existed, were already correctly typed in `lib/api.ts` (`adminServiceJobAssignmentApi`, `adminExecutionApi`), and were **already proven working via live curl** (200, real JSON) — but were never called from any page (dead code). Wired into `/admin/home-services/service-jobs/[jobId]/page.tsx`'s new "Timeline & Notes" section. Live-verified: real Chromium test confirms the section renders with an honest empty state ("No timeline events recorded for this job.") for a job with no real timeline events yet, and the underlying API calls succeed (no error state, no 500).

## What was fixed in FINAL-L5-05C (real, live-verified)
Built the first of 4 required mutation actions against the real `service_jobs`/`service_job_assignments` tables:
- **`POST /v1/admin/service-jobs/{job_id}/reassign`** (super_admin only) — reuses `HomeServiceJobAssignmentService.reassign_job`/`assign_job`, which already existed and already handled tenant checks, staff-eligibility checks, assignment-history preservation (old assignment retired via `is_current=False`/`ASSIGN_STATUS_REASSIGNED`, never deleted), and a real timeline event. Added: the admin-facing endpoint itself, request/error-code mapping to the mission's required contract (404 `JOB_NOT_FOUND`, 403 `JOB_REASSIGN_FORBIDDEN`, 409 `JOB_REASSIGN_NOT_ALLOWED`/`TECHNICIAN_TENANT_MISMATCH`, 422 `TECHNICIAN_NOT_ELIGIBLE`/`REASON_REQUIRED`), and a real `platform_audit_logs` record via `record_platform_audit` (`operation="service_job.reassigned"`, before/after state, actor, tenant).
- **`GET /v1/admin/service-jobs/{job_id}/eligible-technicians`** — new read endpoint so the reassignment UI has a real technician picker, not a raw-UUID text field.
- **`reassignJob`/`getEligibleTechnicians`** added to `adminServiceJobAssignmentApi` in `lib/api.ts`.
- **Real UI**: a `ReassignModal` on the canonical job detail page (`Reassign Technician` button — hidden once a job is `completed`/`cancelled`/`failed`), permission-enforced server-side, technician list from the live endpoint, reason required, confirmation required.
- **L5-05C-001 (real pre-existing bug found and fixed)**: `HomeServiceJobAssignmentService._load_staff` only queried `ProviderTeamMember`, a table that is **completely empty** in real/demo data — every real `service_jobs.assigned_staff_id` value actually references `app.engines.auth.models.User` (role `technician`/`staff`). This meant `reassign_job`/`assign_job`/`list_eligible_staff_for_job` would always fail with `ERR_STAFF_NOT_FOUND` against real jobs, undetected until this sprint's live-API smoke test surfaced it. Fixed with a fallback lookup (`ProviderTeamMember` first for back-compat, then `User`) and a dual-shape `validate_staff_eligibility`. Confirmed via live `curl`: reassignment against a real job (`7caeb8fd-2c6d-4629-be31-e60d940a56a2`) now returns `200` with a real `platform_audit_logs` row and a real `service_job_assignment_events` row, and a real Chromium E2E (`final-l5-05c-reassign.spec.ts`) exercises the full UI flow end-to-end.
- **Known limitation, not fixed this sprint**: the timeline event's `actor_role` is hardcoded to `"provider"` inside the shared `assign_job`/`_emit_event` call, even for admin-initiated reassignments — cosmetically wrong (shows "provider" instead of "super_admin" in the timeline), but the `platform_audit_logs` record (the authoritative audit trail per Part 10) correctly records `actor_role="super_admin"`. Not fixed here because the shared method is also called from the provider-facing flow; changing its default requires threading `actor_role` through both callers, deferred to keep this fix minimal and low-risk.

## What remains a genuine, unclosed gap (Part 2's third allowed outcome: "document a real backend blocker")
Status override, force-close, void, SLA tracking, and summary stats still have **no backend implementation at all** against `service_jobs`/`final_records`. Building real mutation endpoints (with permission checks, audit logging, and duplicate-submission protection per Part 5's requirements) for these 3 remaining mutation actions, plus a summary-stats endpoint and SLA-tracking fields on the `service_jobs` model, is a substantial, multi-endpoint backend + frontend effort that was not safely achievable within this sprint's bounded scope without risking a shallow, unverified implementation of admin-critical job-management mutations. Reassignment was safely achievable because most of its logic already existed and needed disciplined wiring plus one real bug fix, not new domain logic from scratch — the remaining 3 mutations (especially force-close and void, which the mission itself flags as requiring a new completion/deduction policy decision) do not have that head start.

## Result: primary "Jobs" nav item is still NOT migrated
1 of 4 required mutation actions now has real canonical parity; 3 remain (status override, force-close, void), plus SLA tracking and summary stats. Migrating the sidebar's "Jobs" link to the canonical page before all of these are built would still violate rule 5 ("do not remove working job actions") and rule 3 ("do not solve the Jobs defect by only replacing an endpoint string"). The honest, rule-compliant decision remains to leave the primary Jobs nav item on `/admin/operations` (still `/v1/jobs`-backed) until full parity exists. This is the single largest remaining blocker for a clean `READY_FINAL_L5_05_ADMIN_INFORMATION_ARCHITECTURE_CERTIFIED` — see Remaining Blockers.
