### Capabilities canonical has that legacy lacks

## Decision (Part 2 required outcome)
1. **Canonical Jobs list route**: `/admin/home-services/service-jobs` (once parity is closed).
2. **Canonical Jobs detail route**: `/admin/home-services/service-jobs/[jobId]` (once parity is closed).
3. **Create/action ownership**: mutation actions (reassign, status override, force-close, void) do not yet exist against `service_jobs` at all — they must be built (new backend endpoints + new UI), not simply "pointed" at from the canonical page, before the canonical page can safely become primary.
4. **Legacy redirect behavior**: `/admin/operations` keeps its existing real "legacy Field Ops" self-disclosure banner and its link to the canonical page (already present — verified via a new regression test) until migration is complete; it is NOT redirected away yet, because doing so today would silently remove reassign/override/force-close/SLA-tracking/summary-stats from admin users with no replacement.
5. **Removal/deprecation**: not scheduled this sprint — real replacement functionality must exist first (rule 5: "do not remove working job actions").

## What was fixed in FINAL-L5-05C (real, live-verified)
Built the first of 4 required mutation actions against the real `service_jobs`/`service_job_assignments` tables:
- **`POST /v1/admin/service-jobs/{job_id}/reassign`** (super_admin only) — reuses `HomeServiceJobAssignmentService.reassign_job`/`assign_job`, which already existed and already handled tenant checks, staff-eligibility checks, assignment-history preservation (old assignment retired via `is_current=False`/`ASSIGN_STATUS_REASSIGNED`, never deleted), and a real timeline event. Added: the admin-facing endpoint itself, request/error-code mapping to the mission's required contract (404 `JOB_NOT_FOUND`, 403 `JOB_REASSIGN_FORBIDDEN`, 409 `JOB_REASSIGN_NOT_ALLOWED`/`TECHNICIAN_TENANT_MISMATCH`, 422 `TECHNICIAN_NOT_ELIGIBLE`/`REASON_REQUIRED`), and a real `platform_audit_logs` record via `record_platform_audit` (`operation="service_job.reassigned"`, before/after state, actor, tenant).
- **`GET /v1/admin/service-jobs/{job_id}/eligible-technicians`** — new read endpoint so the reassignment UI has a real technician picker, not a raw-UUID text field.
- **`reassignJob`/`getEligibleTechnicians`** added to `adminServiceJobAssignmentApi` in `lib/api.ts`.
- **Real UI**: a `ReassignModal` on the canonical job detail page (`Reassign Technician` button — hidden once a job is `completed`/`cancelled`/`failed`), permission-enforced server-side, technician list from the live endpoint, reason required, confirmation required.
- **L5-05C-001 (real pre-existing bug found and fixed)**: `HomeServiceJobAssignmentService._load_staff` only queried `ProviderTeamMember`, a table that is **completely empty** in real/demo data — every real `service_jobs.assigned_staff_id` value actually references `app.engines.auth.models.User` (role `technician`/`staff`). This meant `reassign_job`/`assign_job`/`list_eligible_staff_for_job` would always fail with `ERR_STAFF_NOT_FOUND` against real jobs, undetected until this sprint's live-API smoke test surfaced it. Fixed with a fallback lookup (`ProviderTeamMember` first for back-compat, then `User`) and a dual-shape `validate_staff_eligibility`. Confirmed via live `curl`: reassignment against a real job (`7caeb8fd-2c6d-4629-be31-e60d940a56a2`) now returns `200` with a real `platform_audit_logs` row and a real `service_job_assignment_events` row, and a real Chromium E2E (`final-l5-05c-reassign.spec.ts`) exercises the full UI flow end-to-end.
- **Known limitation, not fixed this sprint**: the timeline event's `actor_role` is hardcoded to `"provider"` inside the shared `assign_job`/`_emit_event` call, even for admin-initiated reassignments — cosmetically wrong (shows "provider" instead of "super_admin" in the timeline), but the `platform_audit_logs` record (the authoritative audit trail per Part 10) correctly records `actor_role="super_admin"`. Not fixed here because the shared method is also called from the provider-facing flow; changing its default requires threading `actor_role` through both callers, deferred to keep this fix minimal and low-risk.

## What was fixed in FINAL-L5-05D (real, live-verified)
Built 3 more of the 4 required mutation actions against real `service_jobs` data, all in `app/engines/execution/admin_job_actions.py` (one centralized policy service, per the mission's requirement not to scatter transition logic across routers) plus 4 new endpoints on the existing `admin_router` in `app/engines/execution/home_service_router.py` (`/v1/admin/service-jobs/{id}/...`):

- **State-machine grounding**: the real, live `service_jobs.status` values found in production/demo data (`new`, `assigned`, `in_progress`, `completed`, `cancelled`) don't match any single one of the 3 overlapping `JOB_STATUS_*`/`JOB_TRANSITIONS` constant sets already in the codebase (`execution/constants.py`, `final_records/constants.py`, `home_service_assignment/constants.py`) — a real, pre-existing architecture inconsistency, documented here rather than silently papered over. `execution/home_service_service.py`'s `_assert_transition` (using `execution/constants.py`'s `JOB_TRANSITIONS`) is the one gate genuinely enforced at runtime for in-flow transitions. Status override/force-close/void are deliberately terminal-status-based (not dependent on resolving which of the 3 constant sets is "correct"), so they work safely against the real, messy status data without needing that reconciliation first.
- **`GET /v1/admin/service-jobs/{id}/allowed-override-targets`** + **`POST .../status-override`** — a curated, narrow override target set (`cancelled` only, from any non-terminal status) rather than exposing all database status values as frontend options (explicitly forbidden by Part 3). `expected_current_status` optimistic-concurrency check returns `409 JOB_STATUS_CONFLICT` on staleness.
- **`POST .../force-close`** — **Policy A** (derived from `execution/usage_credit_deduction.py`, not guessed): force-close never creates a Completed Job Deduction automatically, because `deduct_for_completed_job` requires resolved `master_service_id`/`offering_type_id`/`brand_id` and real completion evidence that a force-closed job may not have. If genuine completion evidence exists, use the real completion endpoint instead. New terminal status `force_closed` (the `status` column is an unconstrained `String(40)`, so this needed no migration).
- **`POST .../void`** — **BLOCK_VOID_AFTER_DEDUCTION** policy: queries `usage_credit_ledger` for an existing `completed_job_deduction` row for the job; if found, void is refused with `JOB_DEDUCTION_REVERSAL_REQUIRED` rather than silently reversing or rewriting ledger history (rule 15). Live-verified against a real job (`L501-JOB-0004`) that has a real deduction row — the block fires correctly. New terminal status `voided`.
- **Real timeline + audit for every mutation**: each writes a `service_job_execution_events` row (the same table the canonical page's Timeline & Notes section already reads) and a `platform_audit_logs` row via `record_platform_audit`, satisfying Part 11's "verify both operational timeline and platform audit trail."
- **Typed API client**: `getAllowedServiceJobOverrideTargets`, `overrideServiceJobStatus`, `forceCloseServiceJob`, `voidServiceJob` added to `adminExecutionApi` in `lib/api.ts`.
- **Real UI**: `StatusOverrideModal`, `ForceCloseModal`, `VoidModal` on the canonical job detail page — each states its real financial consequence in plain language (force-close: "does not create a deduction automatically"; void: "blocked if a deduction already exists"), requires a reason, requires confirmation, buttons hidden once a job reaches any terminal status.
- **14 new backend unit tests** (`tests/test_final_l5_05d_exceptional_mutations.py`) covering reason-required, stale-conflict, terminal-state protection, disallowed-target rejection, duplicate-force-close, duplicate-void, deduction-blocking, and successful-mutation DB effects for all 3 actions.
- **Live API smoke evidence**: all 3 mutations run against real jobs via curl with real DB verification of job-status/timeline-event/audit-record effects (see bug register).
- **1 real Chromium E2E** (`final-l5-05d-exceptional-mutations.spec.ts`) covering the full status-override UI flow end-to-end against the live dev server.

## What remains a genuine, unclosed gap
SLA tracking and operational summary tracking against `service_jobs` still have **no backend implementation at all**. Building these (Parts 13-15 of the FINAL-L5-05D mission: SLA input inventory, canonical SLA engine, operational summary with reconciled counts and filters) is itself a substantial effort not attempted this sprint to avoid a shallow, unverified implementation. The full 22-row feature-parity re-matrix (Part 21), primary Jobs navigation migration (Part 22), `/admin/operations` redirect (Part 23), and complete removal of active `jobsApi`/`/v1/jobs` usage (Part 24) are all explicitly gated on SLA/summary existing first plus a full parity re-proof — none of that was attempted this sprint either. The 5-role Chromium battery (Part 29) was not run; only the 1 new status-override flow plus the pre-existing reassign/timeline specs were re-verified.

## Result: primary "Jobs" nav item is still NOT migrated
3 of 4 required mutation actions now have real canonical parity (reassign, status override, force-close, void); SLA tracking and summary stats remain the last missing backend capability before a full parity re-proof and navigation migration become possible. Migrating the sidebar's "Jobs" link to the canonical page before SLA/summary exist and full parity is re-proven would still violate rule 5 ("do not remove working job actions") and rule 3 ("do not solve the Jobs defect by only replacing an endpoint string"). The honest, rule-compliant decision remains to leave the primary Jobs nav item on `/admin/operations` (still `/v1/jobs`-backed) until full parity exists. This is now a substantially smaller gap than after FINAL-L5-05C — see Remaining Blockers.
