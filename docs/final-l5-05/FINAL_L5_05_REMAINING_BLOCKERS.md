## Blocker 9 (P0, ESCALATED in FINAL-L5-05G, PARTIALLY CLOSED in FINAL-L5-05H): `TenantWallet`/`tenant_wallets` is real, deeply-integrated package/commission billing infrastructure — not a simple deprecate-and-redirect fix
FINAL-L5-05F's original framing (2 orphaned admin pages) undersold the real scope. FINAL-L5-05G traced the full dependency graph and found `app/engines/platform_commerce/ledger.py`'s wallet functions are called from **12 backend files**, including real package-purchase processing, commission debits/credits, field-ops billing, a real tenant health-score signal (`credit_wallet_health`, 15% weight), and -- critically -- **Security Deposit credit/debit shares the exact same `ledger.py` module**. A third, separately-mounted `/v1/commerce/*` router exposes a job-linked `wallet/deduct` endpoint whose relationship to the certified `Completed Job Deduction` flow was unresolved. `tenant_wallets`/`wallet_transactions` themselves have 0 real rows (no data-migration risk), but the *code paths* are real, wired, and load-bearing. See `FINAL_L5_05G_WALLET_ARCHITECTURE_INVESTIGATION.md` for full evidence.

**FINAL-L5-05H closed the single mandatory P0 sub-gate** (job-deduction architecture comparison, mission Part 7): `engine_deduct_wallet` (`platform_commerce/service.py:372`, exposed as `POST /v1/commerce/tenants/{id}/wallet/deduct`) was confirmed to post to a *different* ledger (`wallet_transactions`) than the canonical Completed Job Deduction (`usage_credit_ledger`), and — critically — had **zero internal callers anywhere in the codebase and zero test coverage**. It was never wired into job completion/force-close/void. Decision: **DEPRECATE_AND_BLOCK**. The route now returns `410 Gone` unconditionally; the underlying service method and shared `ledger.debit_wallet` primitive were left untouched (still used by commission processing and Security Deposits). See `FINAL_L5_05H_JOB_DEDUCTION_GATE.md` for full evidence and verification (Jobs regression guard 12/12 passing including 2 new guards, commerce/wallet/usage-credit suite 130/130 passing, full backend suite re-verified).

**Still open, not attempted in FINAL-L5-05H**: the remaining ~30 parts of the 05H mission — formal per-consumer classification of the other 11 files, endpoint/data-model/mutation-graph/source-of-truth inventories, package-credit/commission/Security-Deposit/tenant-health domain-boundary decisions, a chosen domain-service extraction strategy (A/B/C), actual service extraction, generic wallet API deprecation beyond this one endpoint, `tenant_wallets`/`wallet_transactions` table disposition, DB-level enforcement, RBAC/audit hardening, frontend terminology remediation, and 4-role Chromium E2E. This remains a genuinely large, dedicated-sprint-scale effort — the P0 job-deduction-duplication risk (the one sub-part with an active, evidence-backed correctness risk) is now closed; the rest is architecture cleanup and terminology/IA work, not an active correctness bug.

**FINAL-L5-05I completed the classification 05H deferred.** All 11 remaining consumers were individually classified with real evidence (0 UNKNOWN) — see `FINAL_L5_05I_CONSUMER_CLASSIFICATION.md` and `FINAL_L5_05I_DOMAIN_BOUNDARIES.md`. The true scope proved **larger** than the original 12-file inventory: at least **5 independent "admin adjusts a tenant's credit balance" implementations** (`platform_commerce`, `field_ops`, `tenant_engine`, `package_commerce`, `invoice_payment`) and **2 independent commission-deduction implementations** (`invoice_payment.ServiceCommissionService`, tied to canonical `service_jobs`; `platform_commerce.CommerceService.deduct_commission`, tied to a superseded, 0-row `jobs` table via `field_ops`) exist side by side, none of them reconciled against each other. Concrete new findings:
- **8 active mutation endpoints remain classified AMBIGUOUS_GENERIC** (acceptance criterion #4 not met) — pinned with a new regression guard so the count cannot silently grow, but not reduced this sprint.
- **`package_commerce`'s "Usage Credits" admin endpoints are mislabeled** — gated by `FINANCE_USAGE_CREDITS_*` permissions but mutate `TenantWallet`, not the certified `tenant_billing.credit_balance`. This is the single most product-risk-relevant finding: an admin using the correctly-permissioned UI action adjusts the wrong balance.
- **The tenant health score's `credit_wallet_health` signal (15% weight) has never fired in this environment** — its only writer is unreachable (gated on the same 0-row `jobs` table), so every tenant's health score silently uses the hardcoded default of 100.0 for this signal.
- **`tenant_engine.add_usage_credits`** (the one method in the whole sweep that correctly targets `tenant_billing`) **writes the balance with zero `UsageCreditLedger` row** — a real ledger-evidence gap on the one genuinely-canonical code path found.
- **Security Deposit remains cleanly isolated** — confirmed via source read and a new automated guard test that `credit_deposit`/`debit_deposit` never reference `TenantBilling` or `UsageCreditLedger`.
- A 10-phase, evidence-sequenced migration plan was produced (Phase 0 = this sprint) but **not executed beyond classification and 3 new regression guard tests**, per the mission's explicit instruction not to attempt broad extraction before classification is complete.

**Escalation**: Blocker 9 remains open and is **not downgraded** — the true remediation surface is now known to be 4+ engines and 8 live endpoints, not 2 orphaned pages. This is real evidence that the responsible path continues to be a dedicated, multi-phase migration effort (outlined, not attempted), consistent with FINAL-L5-05G's and FINAL-L5-05H's own conclusions.
