## Blocker 14 (P0, NEW in FINAL-L5-05S): `compliance_sla.py`'s background loop has apparently silently no-op'd on every tick since its own introduction — unrelated to Enterprise Export, discovered as a byproduct
While building this sprint's own export worker (deliberately modeled on `compliance_sla.py`'s pattern, described in this engagement's history as "proven in production"), the worker's first automated test run immediately threw `ImportError: cannot import name 'AsyncSessionLocal' from 'app.database'` — that name does not exist anywhere in `app/database.py` (the real API is `get_session_factory()`). Grepping the codebase for the same import shows `app/jobs/compliance_sla.py` uses the identical nonexistent import at 2 call sites. Because its background loop wraps every tick in `except Exception: log, don't crash`, this means the SLA-compliance background job has been silently failing — `ImportError`, caught, logged, discarded — on every single tick since it was built, and has apparently never once successfully executed against a real database in this environment. `tests/test_p0_compliance_sla_automation.py`'s entire suite is static source-inspection only (e.g. `assert "AsyncSessionLocal" in self._src()`), so this was never caught by any existing test. **This sprint's own new code had the same bug and was fixed** (`export_worker.py` now correctly uses `get_session_factory()`); **`compliance_sla.py` itself was deliberately left unfixed**, since repairing it is unrelated to Enterprise Export and outside this mission's explicit scope boundary. A future sprint must treat this as a P0: SLA breach detection, a real business-critical monitoring function, has apparently never actually run in this environment.

While building FINAL-L5-05T's global duplicate-route detector (which required fixing a route-flattening bug — `app.routes` contains `_IncludedRouter` wrapper objects in this FastAPI version, not a flat `APIRoute` list, causing naive route-table inspection to silently see 0 routes), the corrected detector found **18 real `(method, path)` duplicate registrations completely unrelated to Service Areas**: Customer Addresses (`GET /v1/admin/customers/{customer_id}/addresses` — serviceability vs. auth.admin_customers_router), Engine Health (`GET /v1/admin/engines` and `/v1/admin/engines/health` — engine_mgmt vs. provider_portal), Finance Summary (`GET /v1/admin/finance/summary` — finance_hub vs. field_ops), Tenant Wallet (5 routes — field_ops vs. tenant_engine, both tenant-portal and admin-side), Service Options (5 routes — admin_catalog.admin_router vs. admin_catalog.service_option_admin_router), Staff Job Accept/Reject (2 routes — home_service_assignment vs. execution), and Analytics Alerts (`GET /v1/admin/analytics/operational-alerts` — analytics.admin_router vs. analytics.platform_router). Each pair means one handler is silently shadowed dead code, the exact same defect class FINAL-L5-05T fixed for Service Areas — the wallet duplication in particular is concerning given the platform's long history of `TenantWallet`/`tenant_billing` confusion (Blocker 9 lineage). **Not investigated or fixed this sprint** — explicitly outside FINAL-L5-05T's bounded Service Area scope. Documented, allowlisted with justification in the new global detector (pinned so the allowlist cannot silently grow or go stale), and logged as a new, real blocker requiring the same remediation pattern as FINAL-L5-05T itself: runtime inventory, parity comparison, canonical-owner decision, removal, one domain at a time.

## Blocker 17 (P0, RESOLVED in FINAL-L5-05U): Security Deposit permission-namespace duplication — FULLY CLOSED
FINAL-L5-05O identified frontend/backend Security Deposit permission-namespace duplication and applied a bounded fix (granting Finance Admin both namespaces) without reconciling the underlying architecture. FINAL-L5-05U's own inventory found the true scope was worse: **three** independent live implementations (`finance_hub`, `package_commerce`, `platform_commerce`) against the same tables, with a precisely-located root cause for the frontend/backend mismatch — the dedicated `/admin/finance/deposits` page's nav item and page-level `RequirePermission` route guard checked the deprecated `finance.security_deposits.read` namespace while the SAME page's own action menu and every backend endpoint it calls checked the canonical `finance:deposits:*` namespace, meaning no role could both see and successfully use the page without holding both.

**Resolution**: `FINANCE_DEPOSITS_*` selected as sole canonical family via a full ADR. The deprecated namespace's 8 constants remain defined (frozen, marked deprecated) but removed from every role bundle and pinned by an automated guard so they can never again authorize a live endpoint. Two real, previously-unknown bugs found and fixed as byproducts: a transactional-integrity defect in `package_commerce`'s now-blocked (410) implementation (refund/forfeit mutated status without ever moving money through the ledger) and a genuine cross-tenant read vulnerability in `platform_commerce`'s tenant self-service deposit endpoints (no tenant-ownership check at all — fixed mirroring `ServiceabilityService._assert_owns_tenant()`'s established FINAL-L5-05Q pattern). Two real ungated frontend controls (Export button, Adjust Security Deposit menu item) are now correctly permission-gated. All fixes live-verified via a real 5-role API matrix, real cross-tenant denial, real audit/balance confirmation via direct database query, and 2 new real-Postgres concurrency/isolation tests.

**Status**: **FULLY CLOSED** for the permission-namespace/cross-tenant scope. See `FINAL_L5_05U_ADR_SECURITY_DEPOSIT_CANONICAL_PERMISSION.md` for complete evidence. **Residual, honestly-documented gaps**: no browser-automation tool was available this session (Chromium/responsive/accessibility/performance evidence not captured — same limitation as FINAL-L5-05S/05T); no Security Deposit settings/configuration feature exists to certify (confirmed genuinely absent, not built — out of this reconciliation mission's bounded scope).
