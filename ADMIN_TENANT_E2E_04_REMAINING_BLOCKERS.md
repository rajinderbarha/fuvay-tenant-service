# Remaining Blockers (ADMIN-TENANT-E2E-04)

None of these block certification (all are documented, non-fabricated, real findings that fall short of the spec's explicit NOT_READY triggers):

1. **Two parallel job-data systems** — `/admin/operations` (Operations Board, legacy `jobs` table, currently 0 rows) vs. `/admin/home-services/service-jobs` (Home Services `service_jobs` table, 11 real rows including 1 completed). Only one has real Home Services data today. Recommend either (a) migrating the Operations Board to also read `service_jobs`, or (b) building a dedicated `/admin/home-services/service-jobs/[id]` detail page that reuses the existing `/admin/operations/[jobId]` UI pattern (payment/deduction record, timeline) against the `service_jobs`/`usage_credit_ledger` data model.
2. **`service-jobs` "View Details" row action links to a non-existent route** (`/admin/home-services/service-jobs/{id}` has no page file) — will 404 if clicked. Follow-up: build the detail page per item 1, or repoint the link to `/admin/operations/{id}` once item 1's data-source unification happens.
3. **`service-jobs` grid is missing several spec-requested columns** (Customer, Service, Type, Brand, Selected Price, Payment Mode) — currently only Job #/Status/Assignment/Tenant(hidden)/Created.
4. **Today's freshest real completed job (`JOB-20260710-000001`) has no usage_credit_ledger entry yet** — the deduction-posting mechanism is proven correct from two older (2026-07-09) real ledger rows for now-superseded job IDs, but has not fired for the current session's completed job. Likely a scheduled/triggered job that hasn't run yet, or a manual dev-flow step not yet exercised on this specific job. Not fabricated as fixed — documented honestly per spec Part 9 instruction.
5. **`request_id` not shown on successful (non-error) matching/no-match results** — only surfaced on the error path (`SectionError`). The data contract includes it (confirmed via curl `meta.request_id`); a minor UI enhancement to also show it as fine-print on success would improve traceability.
6. **`service-jobs/page.tsx` bypasses the central API client** with a direct `fetch()` (manual token/header handling), unlike every other in-scope page. Functionally correct (real backend, real auth) but inconsistent with the established `lib/api.ts` pattern, and loses automatic request_id surfacing.
7. **Bookability is narrative, not a per-check pass/fail grid with last-checked timestamps** on the matching pages — real, correctly-gating, and never misleading, but does not match the spec's literal "individual pass/fail rows + last-checked time" ask. A dedicated bookability detail view (distinct from the already-existing but out-of-scope `/admin/bookability/providers`) would close this gap.
8. **Completed Job Deduction config page lacks Effective From/To, Created By, Updated At columns** and does not independently confirm a DB-level `CHECK (deduction_credits >= 0)` constraint exists (relies on the Pricing Rules CRUD layer's validation, already certified in E2E-03, not re-verified here).
9. Carried forward from prior sprints (E2E-01/02/03), unchanged, out of this sprint's scope: no `npm test` script configured; notification bell has no click handler; hardcoded role label "Platform"; nav-config.ts/AdminLayout.tsx sidebar drift (several real pages have no sidebar entry).

None of the above were assessed as "broken" or "misleading" per the spec's strict NOT_READY criteria — all core matching/no-match/deduction-config/payment-copy functionality is real, live, and correct.
