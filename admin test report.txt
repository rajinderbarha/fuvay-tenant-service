SUMMARY
====================================================================
- 146 static admin routes were enumerated from app/admin/**/page.tsx (dynamic [id]/[key] detail routes
  excluded from the bulk crawl, a handful spot-checked manually) and crawled with Playwright, logging
  every console error and every HTTP >=400 response per page.
- Pages fully verified working with real backend data via manual, non-automated interaction: Dashboard,
  Verticals (list + counts cross-checked against DB), Tenants (list rendered, permission gate observed),
  Login flow (real JWT issued and stored).
- Pages with a CONFIRMED real defect (network error, wrong endpoint, or CORS failure independent of the
  session-cascade bug described below): 7 pages (see "Confirmed Defects" below).
- CRITICAL systemic bug found: a single 401 from an unrelated/broken endpoint on ANY page silently wipes
  the admin's session (token cleared from localStorage) and cascades 401s across every subsequently
  visited page for the rest of the browser session, with no redirect to /login and no visible toast/banner
  explaining what happened. See "Most Severe Issues" #1.
- IMPORTANT CAVEAT ON METHODOLOGY (read before the per-page notes): the automated crawl used
  Playwright's `page.goto(url, { waitUntil: 'load' })`. In this dev environment the Next.js dev server's
  Fast-Refresh/HMR websocket connection appears to prevent the browser "load" event from firing reliably,
  so ~67 of the 146 crawled pages were flagged "LOADERR" (goto timeout) by the automated pass. I manually
  re-verified two of these (Verticals, Tenants) with a longer wait and confirmed they DO render correctly
  with real data — the "LOADERR" flag is a crawl-methodology false positive in most cases, not proof of a
  broken page. I did NOT have time to manually re-verify all 67 flagged pages individually; they should be
  treated as "not conclusively tested" rather than "confirmed broken" except where a genuine console/network
  error was also captured (those are listed explicitly below).
- Full interactive click-through CRUD (create -> edit -> reload-verify -> delete) was NOT completed across
  all 146 pages in this session — that would require many hours against this dev-mode server, whose
  per-route first-compile time is 5-20 seconds and whose Fast Refresh cycles interrupt in-flight form
  submits (observed directly: a login submit was silently converted into a native (non-JS) form GET
  navigation mid Fast-Refresh rebuild — see "Most Severe Issues" #3). I completed full CRUD-style
  verification only on the Verticals enable/disable path (see below); other CRUD surfaces (Packages,
  Tenants approve/reject, Complaints, Staff) were confirmed to LOAD with real data but their create/edit/
  delete actions were not each individually clicked through. This is disclosed explicitly rather than
  guessed at.

MOST SEVERE ISSUES (prioritized)
====================================================================

1. [CRITICAL] Single unrelated 401 silently logs the whole admin session out, with no redirect and no
   warning banner — every page visited afterward in that browser session appears broken.
   Root cause (frontend/super-admin/lib/api.ts, apiFetch(), ~line 75-101): when ANY apiFetch() call gets
   HTTP 401, the code tries a refresh_token; since super-admin login here returns
   refresh_token: null (confirmed via curl to /v1/auth/login), the refresh path is skipped and
   clearSession() is called immediately, wiping the access token from localStorage. Every other page's
   own unrelated API calls (e.g. /v1/auth/me, /v1/admin/notifications/unread-count) then also 401 because
   the token is gone, and the UI shows either a blank page or a generic "Permission denied — You do not
   have access to this page" banner instead of returning the user to /login.
   Repro: visit /admin/refund-requests (see bug #2 below, which triggers a spurious 401), then visit
   /admin/review-flags, /admin/staff, /admin/tenants, /admin/users, etc. — all fail with 401s on
   /v1/auth/me even though the admin never explicitly logged out. In the automated crawl this cascade
   affected 29 subsequent pages (alphabetically after refund-requests): account/login-history unrelated,
   review-flags, review-replies, reviews, rework-requests, security, service-coverage, service-setup and
   all its sub-pages, staff, support, tenants, tenants/onboarding-requests, trust-quality, types-brands,
   users, users/permissions, users/roles, workflow-templates.
   Impact: any single flaky/broken endpoint anywhere in the app can silently deauthenticate the operator
   platform-wide mid-session with no explanation, which is a serious operability/trust problem for a
   super-admin console.

2. [HIGH] /admin/refund-requests calls the WRONG backend endpoint.
   Observed network call from that page: GET /v1/admin/real-estate/lead-drafts?limit=50 -> 401.
   This is a real-estate/lead-drafts endpoint, unrelated to refund requests — looks like copy-pasted
   fetch wiring that was never repointed at the actual refunds endpoint. This is also the trigger for
   Issue #1's cascade in a normal crawl order.

3. [HIGH — environment/process finding, not itself a product bug, but affects testability] The login
   form's onSubmit handler can be pre-empted by a Next.js Fast-Refresh rebuild in dev mode: when a Fast
   Refresh cycle fires at the moment the Login button is clicked, the click was observed to fall through
   to a native HTML form submission (full-page GET to /login?) instead of invoking the React handler
   (which calls authApi.login and does client-side navigation). This only reproduces when the dev server
   is actively recompiling; it did not reproduce once the dev server was warmed up and idle. Flagging
   because it cost significant debugging time and would also affect any other automated tooling
   (e2e/CI) run against a cold Next dev server.

4. [MEDIUM] /admin/analytics/alerts: GET /v1/admin/analytics/providers/performance?date_from=...&date_to=...&sort_by=completed_jobs
   returns HTTP 500. Real backend error, independent of the cascade bug (this page was visited before
   the cascade started).

5. [MEDIUM] /admin/home-services/customers: GET /v1/admin/pricing-rules?page=1&page_size=200&sort_by=priority&sort_dir=desc
   returns HTTP 404. A customers-list page should not be calling a pricing-rules endpoint at all —
   looks like another mismatched/copy-pasted API call similar to Issue #2.

6. [MEDIUM] /admin/marketing/automation: GET /v1/admin/marketing/assets?page=1&page_size=20 -> 404.
   This is consistent with prior findings in project memory (MODULE-L5-44) that the marketing
   assets/templates backend was genuinely removed/superseded — this page is calling a feature that no
   longer exists server-side and has no honest-disclosure banner for it (unlike the pages L5-44 fixed).

7. [MEDIUM] /admin/ai/metrics and /admin/marketing/generate both hit CORS failures in the browser
   console:
     - ai/metrics: fetch to /v1/admin/ai/failed-actions?limit=100 blocked by CORS ("No
       'Access-Control-Allow-Origin' header").
     - marketing/generate: fetch to /v1/admin/marketing/events?event_type=undefined&limit=100 blocked by
       CORS. Note the literal string "undefined" serialized into the query string — a frontend bug where
       an unset/undefined event_type filter is being sent as the string "undefined" instead of omitted.
   Both are consistent with the backend returning an error response without CORS headers (FastAPI's
   CORS middleware typically only adds headers to successful/handled responses; an unhandled 500 or a
   route that doesn't exist can surface as a CORS error in the browser even though the real problem is
   the missing/broken route).

8. [LOW] /admin/account/login-history: GET /v1/auth/api-keys -> 403. Login-history page pulling from an
   API-keys endpoint the current session isn't authorized to call; either a permissions gap or another
   mismatched endpoint.

9. [LOW] /admin/service-groups: browser reported net::ERR_CONNECTION_RESET on one resource during the
   crawl. Only seen once; could not conclusively rule out a transient backend hiccup vs. a real problem.
   Recommend re-testing in isolation.

CONFIRMED NEW DEFECTS THIS ROUND:

Issue #9 — Vertical detail page calls a dead pricing-rules endpoint on every load.
  Page: /admin/verticals/home_services (and presumably every other vertical detail page — same
  component).
  Repro: load the page; browser console immediately logs two "Failed to load resource: 404" errors for
  GET http://localhost:8000/v1/admin/pricing-rules?page=1&page_size=50&sort_by=priority&sort_dir=desc.
  Confirmed independently via curl:
    curl http://localhost:8000/v1/admin/pricing-rules?page=1&page_size=50&sort_by=priority&sort_dir=desc
    -> {"error_code":"NOT_FOUND","detail":"Not Found", ...} (HTTP 404)
  The route simply does not exist on the backend under that path (there's no bare /v1/admin/pricing-rules
  endpoint registered — pricing rules likely live under a different, more specific path, e.g. scoped by
  tenant or vertical). Effect: whatever widget/section on the vertical detail page is meant to show
  pricing rules silently fails to load every single time, on every vertical. Did not chase down which
  exact frontend component fires this call (fired on initial page load, before any tab is clicked) or
  find the correct backend path it should be calling — that would need a source-level look at the
  vertical detail page's component code plus the pricing-rules router.

Issue #10 — Staff detail page's "jobs" widget hits a crashing (500) backend endpoint, and the failure
  is asynchronous/delayed enough that it doesn't surface until the admin has already navigated away.
  Page: /admin/staff/[id] (tested with staff id 8d436e44-c87d-4c4a-bb16-f3b6e8b36448).
  Repro:
    curl http://localhost:8000/v1/admin/staff/8d436e44-c87d-4c4a-bb16-f3b6e8b36448/jobs?page=1
    -> HTTP 500 {"error_code":"INTERNAL_ERROR","detail":"An unexpected error occurred...", ...}
  In the browser, this endpoint's failure did NOT appear in the console while the staff detail page
  itself was the active route — it only appeared moments later, attributed (by our per-route error
  bucketing) to whichever page was loaded *next* (in this run, /admin/categories/[id]), and it was
  reported by the browser as a CORS failure ("blocked by CORS policy: No 'Access-Control-Allow-Origin'
  header is present"), not as a 500. This is a second, compounding bug: FastAPI's generic 500 error
  handler is evidently not passing the request through the CORS middleware the way normal responses are,
  so a genuinely crashing endpoint presents to the browser as a same-origin-policy violation instead of
  a server error — actively misleading for anyone debugging from the browser console alone, since "CORS
  error" and "backend 500" point a developer in very different directions. Net effect for the end user:
  the staff detail page's jobs section quietly never loads (no visible on-page error was captured, though
  full visual/screenshot confirmation of the widget's on-page failure state was not done this round), and
  the underlying crash is only discoverable by reading the Network tab or curling the endpoint directly.
